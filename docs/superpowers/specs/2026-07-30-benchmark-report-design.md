# Benchmark report on `gh-benchmarks` — design

## Problem

`benchmark-cog.yml` and `benchmark-mosaic.yml` each produce two JSON files
(`benchmark.json` from pytest-benchmark, `siege_results.json` from siege) but
never persist them anywhere. We want to store the latest results somewhere
durable and serve a custom HTML dashboard from them.

## Decisions

- **Scope: latest run only.** No historical trend charts, no per-run archive.
  Each CI run overwrites the previous result for its own workflow (cog or
  mosaic). Revisit if trend charts are wanted later — the branch layout below
  doesn't preclude adding a dated/sha history path in the future.
- **Branch: reuse the existing `gh-benchmarks` orphan branch** (already on the
  remote, already referenced in both workflows' `permissions: contents: write`
  comment) rather than creating a separate `gh-pages` branch. GitHub Pages will
  be pointed at `gh-benchmarks` / root.
- **One unified report page** covering both cog and mosaic benchmarks, as
  stacked sections (COG above Mosaic), not tabs.
- **Static HTML, client-side fetch.** `index.html` is committed once and never
  regenerated by CI. It fetches the JSON data files at page load and renders
  in the browser. CI's only job is to push the 4 JSON files. No Python/Jinja
  report-generation step, no server-side templating.
- Raw JSON files (`benchmark.json`, `siege_results.json`, and the intermediate
  `output.json`) live **only** on `gh-benchmarks`, never on `main`. `main`'s
  `.gitignore` gets these three filenames added so local test runs don't show
  up as untracked files in `git status`.

## Branch layout (`gh-benchmarks`)

```
gh-benchmarks/
  index.html                  # static report, committed once
  cog/benchmark.json          # overwritten by benchmark-cog.yml
  cog/siege_results.json      # overwritten by benchmark-cog.yml
  mosaic/benchmark.json       # overwritten by benchmark-mosaic.yml
  mosaic/siege_results.json   # overwritten by benchmark-mosaic.yml
```

Seeded once with `index.html` + empty `cog/`, `mosaic/` directories in a single
initial commit to the orphan branch.

## Data shape changes

**siege_results.json.** Current jq output embeds the service name inside
`name`:

```json
{"name": "titiler elapsed_time", "unit": "s", "value": 87.10}
```

This forces the report's JS to string-parse the service back out of the
label. Change the jq filter in both workflows to split it into two fields:

```json
{"service": "titiler", "name": "elapsed_time", "unit": "s", "value": 87.10}
```

Applies to all three service blocks in `benchmark-cog.yml` (titiler,
async-titiler) and all three in `benchmark-mosaic.yml` (titiler-pgstac,
titiler-stacapi, async-titiler-stacapi).

**benchmark.json.** Corrected from the original draft: the committed
`benchmark.json` is *not* the raw pytest-benchmark output — the workflow
already reduces it to a bare array via
`jq '.benchmarks[] | {name, group, stats}' | jq '[inputs]'`, which drops
`commit_info` and `datetime` entirely. Since the report header needs commit
sha + datetime, change the jq to a single call that wraps the array and keeps
those two fields:

```bash
cat output.json | jq '{commit_info: .commit_info, datetime: .datetime, benchmarks: [.benchmarks[] | {name: .name, group: .group, stats: .stats}]}' > benchmark.json
```

New shape: `{"commit_info": {...}, "datetime": "...", "benchmarks": [{"name", "group", "stats"}, ...]}`.
This also collapses the existing double-jq-pipe into one call.

## Workflow changes

Both workflows currently trigger on `push` (to `main`) and `pull_request`. New
steps only run on `push`:

```yaml
if: github.event_name == 'push'
```

This avoids giving PR runs (including from forks) write access to shared
benchmark history, and avoids two untrusted runs racing to push.

Steps appended after the existing "Merge Outputs" step, gated as above:

1. Checkout `gh-benchmarks` into a subdirectory (e.g. `gh-benchmarks/`), using
   `actions/checkout` with `ref: gh-benchmarks` and `path: gh-benchmarks`.
2. Copy that job's `benchmark.json` and `siege_results.json` into
   `gh-benchmarks/cog/` (cog workflow) or `gh-benchmarks/mosaic/` (mosaic
   workflow).
3. Commit and push using `stefanzweifel/git-auto-commit-action` scoped to the
   `gh-benchmarks` checkout, targeting branch `gh-benchmarks`. This action
   fetches/rebases before pushing, which matters because the cog and mosaic
   workflows can run concurrently and each pushes to the same branch (though
   to different subdirectories, so real conflicts are unlikely — the action
   just makes the push itself safe without hand-rolled retry logic).

## Report page (`index.html`)

Static file, plain HTML/CSS/JS, no build step, no external libraries (works
directly from GitHub Pages).

**Data loading:** on page load, `fetch()` all four JSON files
(`cog/benchmark.json`, `cog/siege_results.json`, `mosaic/benchmark.json`,
`mosaic/siege_results.json`). If a fetch fails (404 — e.g. mosaic hasn't run
yet on a freshly seeded branch), that section renders a "no data yet"
placeholder instead of breaking the page.

**Header:** report title, commit sha and datetime — read directly from
whichever `benchmark.json` loaded first (cog's or mosaic's; both are stamped
from the same `main` commit history), using its existing `commit_info` /
`datetime` fields. No separate metadata file needed.

**Layout:** stacked sections, COG then Mosaic. Each section has:

- A grouped bar chart: one group per `group` (zoom bucket from
  `benchmark.json`, e.g. `"Zoom 3"` or `"Zoom 0 - 15 Assets"` for mosaic), one
  bar per service (`name`), bar height = `stats.mean` latency. Built as plain
  HTML/CSS bars (flexbox, no chart library) per the dataviz skill spec: bars
  ≤24px thick, 4px rounded caps, 2px gaps between bars, legend always present
  for 2+ series, hairline baseline, value labels at the bar tip.
- A table below the chart for siege metrics (elapsed time, response time,
  transaction rate, concurrency), one row per metric and one column per
  `service` (from the updated siege JSON shape above).

**Color:** dataviz skill's default categorical palette — slot 1 (blue) /
slot 2 (orange) for cog's two services, + slot 3 (aqua) for mosaic's third
service. Both light and dark (`prefers-color-scheme`) are styled, using the
palette's light/dark steps.

Confirmed via browser mockup during brainstorming (stacked layout, chosen
over a tabbed alternative).

## GitHub Pages setup

`gh-benchmarks` is currently an empty orphan branch with no files. Rollout:

1. Seed `gh-benchmarks` with `index.html` + empty `cog/`, `mosaic/` dirs in
   one commit.
2. Enable GitHub Pages in repo settings (Settings → Pages → source:
   `gh-benchmarks` branch, `/` root). This is a repo-settings change, done
   either manually in the GitHub UI or via `gh api` with explicit user
   go-ahead — not part of the workflow YAML.
3. Land the workflow changes (siege jq shape, push-to-gh-benchmarks steps).
4. Trigger each workflow once (push or manual dispatch) and confirm
   `gh-benchmarks` receives fresh `cog/*.json` / `mosaic/*.json`.
5. Open the Pages URL and confirm the report renders both sections with real
   data (not just the mockup's sample numbers).

## Out of scope

- Historical/trend charts across runs.
- PR-triggered publishing of benchmark data.
- Alerting/regression-threshold PR comments (this was the `github-action-benchmark`
  approach; explicitly dropped in favor of a custom report).
